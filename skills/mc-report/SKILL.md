## 触发条件

当用户提到以下任意情形时使用本技能：

- "复盘" / "周报" / "月报" / "总结"
- "这个 campaign 效果怎么样"
- "帮我写一份复盘报告"
- 提供了执行数据（曝光、互动、转化等）

---

## 工作方式

1. 读取 `campaigns/{project-slug}/` 下的所有文件作为计划上下文
2. 要求用户提供执行数据（如未提供）：
   - 各平台曝光量、互动数据（点赞/收藏/评论/转发）
   - 转化数据（点击率、留资量、成交量）
   - 预算消耗情况
   - 如果用户说"没有数据"，基于 campaign 计划做预测性复盘框架
3. 产出写入 `campaigns/{project-slug}/report.md`

```markdown
## 一、目标回顾

| 指标 | 目标值 | 实际值 | 达成率 | 判断 |
|------|--------|--------|--------|------|

## 二、关键发现

### 做对了什么
1. {具体发现，不是"内容质量好"，是"小红书角度 A 的互动率达到 X%，高于行业均值"}
2. ...

### 做错了什么

每条问题都要把**触发因素**和**根本原因**分开写——这两件事对应完全不同的下一步，混成一句话是复盘最常见的失效方式。

- **触发因素**：这一次为什么发生（具体的、一次性的导火索）
- **根本原因**：为什么系统允许它发生（不修的话，换个时间换个人还会再来一次）

| # | 问题现象 | 触发因素（这次为什么发生） | 根本原因（为什么还会再发生） | 修复归属 |
|---|---------|--------------------------|---------------------------|---------|
| 1 | {现象} | {一次性导火索} | {系统性缺陷} | {流程 / 技能 / 人力 / 预算} |
| 2 | | | | |

示例：投放首日超支 40%
- 触发因素：新建广告组误填日预算，多加一个零
- 根本原因：预算变更没有二次确认环节，单人操作即可生效
- 只修触发因素 = 提醒本人下次小心；修根本原因 = 加一道复核，这才是复盘的价值

**写作纪律：**
- 归因到系统和流程，不归因到人——"某某不细心"不是根本原因，"没有复核机制"才是。
- 根本原因写不出来时，标注 `⚠️ 根因未定位`，不要用触发因素凑数。留白比伪结论有用，下次复发时能立刻看出这里一直没查清。
- 与 mc-diagnose 的分工：本技能是事后复盘（已知结果找原因），mc-diagnose 是实时诊断（症状未明找病灶）。复盘中发现根因跨多个环节、需要系统排查时，路由到 mc-diagnose 走八维框架，不要在复盘里硬做诊断。

### 意外发现
1. {未预期的正面或负面信号}
2. ...

## 三、平台表现

### {平台 1}
- **数据：** 曝光 / 互动 / 转化
- **高表现内容：** {哪类内容效果最好}
- **低表现内容：** {哪类内容效果差}
- **优化方向：** {下次怎么调}

### {平台 2}
...

## 四、预算复盘

| 分配项 | 计划预算 | 实际消耗 | ROI / 效率指标 |
|--------|---------|---------|---------------|

## 五、竞品动态回顾

{活动期间竞品有什么新动作，对我方有什么影响}

## 六、可复用经验

| 经验 | 适用场景 | 具体做法 |
|------|---------|---------|

## 七、下一步计划

| 优先级 | 动作 | 负责方 | 预期时间 |
|--------|------|--------|---------|

## 八、团队建议

{对团队配合、流程、工具的改进建议}
```

## 复盘质量标准

- **数据驱动**：每个结论必须有数据支撑，没有数据的写"待补充数据"
- **归因到动作**：不是"效果不好"，是"抖音第二条视频完播率只有 X%，原因是前 3 秒没有钩子"
- **可操作**：每条建议必须可执行，不是"加强内容质量"，是"下次小红书标题改用提问句式，参考角度 A 的互动数据"
- **不甩锅**：问题归因到动作和决策，不归因到人

## 记忆回写（复盘后必做）

report.md 写入完成后，把本次 campaign **验证或证伪的假设**蒸馏回品牌长期记忆，
让洞察跨 campaign 复利——这是复盘的最后一步，不是可选项：

1. 从「关键发现」「可复用经验」中提取 ≤3 条**已被数据验证**的洞察
   （格式：`{结论} — 验证于 {campaign-slug}，证据：{数据点}`）
2. 提取 ≤2 条**被证伪的假设**（策略阶段的判断被实际数据推翻的）
   （格式：`{原假设} — 证伪于 {campaign-slug}，实际：{数据点}`）
3. 按下方「品牌记忆格式」追加到 `memory/brand-memory.md`（或多品牌路径）常驻层的
   `## 已验证的核心洞察`：只追加不覆盖，语义重复跳过，按 campaign slug 去重；
   若该结论对应 `## 待验证洞察` 里的某条，在那条末尾加 `⚠️ 已于 {campaign-slug} 验证 / 证伪`
4. 无执行数据的预测性复盘**不回写**（未经验证的判断不能进入长期记忆）

回写完成后在交付卡中加一行：`🧠 品牌记忆：+{N} 条验证洞察 / +{M} 条证伪记录`

---

## 交互规则

- 用户可以分批提供数据（"先给你小红书的数据"），系统先输出已有部分，后续补充
- 用户可以要求不同粒度："简版复盘"（一页纸）vs "完整复盘"
- 如果没有执行数据，系统输出"复盘框架"：列出应该追踪的指标和数据维度
- 复盘报告可以独立使用，不依赖完整 campaign 流程

## 通用纪律

### 产出流程

由 mc-cmo 路由或 mc-orchestrate 编排时，slug 和执行流程以调用方为准，跳过本节。用户用 `/mc-report` 直接调用时，按以下步骤落盘，让文件、`.status.json` 与 WebUI 保持一致：

1. 定位脚本（对话中探测一次）：
   ```bash
   for base in "${MC_HOME:-}" ~/.openclaw ~/.claude ~/.hermes .; do
     [ -n "$base" ] && [ -f "$base/scripts/setup.mjs" ] && SCRIPTS_DIR="$base/scripts" && break
   done
   echo "${SCRIPTS_DIR:-scripts not found}"
   ```
2. 确定 slug：`{品牌/产品}-{场景}-{市场}`，全小写连字符；无法推断时用 `campaign-{YYYYMMDD}`。已有同名 campaign 时沿用。
3. 加载上下文：`campaigns/{slug}/` 下已有 brand.md、storyteller.md、insight.md 等上游产出时，先读取再动笔（mc-cmo 路由时会自动注入，直接调用时由本技能自己读）。
4. 初始化：`node "$SCRIPTS_DIR/setup.mjs" --slug "{slug}" --skill "mc-report" --step "report"`
5. 把完整产出（含交付卡）写入 `/tmp/mc-{slug}-report.md`，不在对话中输出正文。
6. 后处理：`node "$SCRIPTS_DIR/finalize.mjs" --slug "{slug}" --step "report" --file "report.md" --skill "mc-report" --input /tmp/mc-{slug}-report.md`，把输出原样返回用户，不添加任何内容。
7. 找不到脚本或没有 node 时不要中断：
   - 直接把产出写入 `campaigns/{slug}/report.md`；
   - `.status.json` 不存在时先写入 `{"campaignSlug":"{slug}","status":"running","steps":{},"review_loop":{"iteration":0,"max":3}}`，再把 `steps.report` 记为 `{"status":"done","file":"report.md"}`；
   - 对话中只输出交付卡，并在其下加一行 `⚙️ 降级模式：未使用 setup/finalize 脚本（WebUI 状态可能不实时）`。

### 品牌记忆格式

读写 `memory/brand-memory.md`（多品牌：`memory/{brand-slug}/brand-memory.md`，slug 取自 `brief.md` 的 `brand:` 字段）时，只用下表章节，章节名一字不改、顺序不变：

| 层 | 章节 | 写什么 | 谁写 |
|----|------|--------|------|
| 常驻层 | `## 品牌定位` | 一句话定位、核心价值主张 | mc-brand |
| 常驻层 | `## 品牌人格与语调红线` | 人格关键词、语调风格、有效表达、禁用词与风格禁区、叙事风格 | mc-brand、mc-storyteller |
| 常驻层 | `## 当前主推` | 当前主推的产品或活动 | 用户（经 mc-memory） |
| 常驻层 | `## 已验证的核心洞察` | 只收有执行数据证据的结论：`{结论} — 验证于 {slug}，证据：{数据点}` 或 `{原假设} — 证伪于 {slug}，实际：{数据点}` | mc-report、用户（经 mc-memory） |
| 分隔 | `<!-- ARCHIVE BELOW · 常驻层到此为止，以下为档案层，按需加载 -->` | 常驻层每次对话都会被加载；以下内容只在需要历史时读取 | — |
| 档案层 | `## 待验证洞察` | 尚未经执行数据验证的洞察与风险预警：`{内容}（待验证，来源：{slug}，{日期}）` | mc-insight |
| 档案层 | `## Campaign 历史` | 表格 `\| slug \| 日期 \| 核心目标 \| 关键结论 \|`，同一 slug 只留一行 | 所有写回技能 |
| 档案层 | `## 诊断记录` | `### {日期} — {诊断模式}` + 症状 / 根因 / 修复状态 / 关联技能 | mc-diagnose |
| 档案层 | `## 历史洞察（含已过期）` | 压缩时从常驻层移出的条目，原文不改 | mc-memory |

**规则：**
- **未经执行数据验证的判断不得写入常驻层。** 常驻层每次都会被优先加载，写进去的假设会被下游当成事实。
- **文件不存在：** 按上表顺序创建全部章节（含分隔标记）后再写入。
- **旧格式文件**（缺上表章节或缺分隔标记）：先迁移再写入，只调整条目所在章节，不改条目原文——`品牌核心` → `品牌定位`，`品牌声音` → `品牌人格与语调红线`，`已验证洞察` 中带 `验证于` / `证伪于` 证据的条目 → `已验证的核心洞察`、其余 → `待验证洞察`，`踩过的雷` → `待验证洞察`（条目前加 `风险预警：`）；缺的章节按顺序补齐，并插入分隔标记。
- **写入前比对本章节已有条目：** 语义相同 → 跳过；同一主题结论不同 → 追加新条目，并在旧条目末尾加 `⚠️ 已被 {新条目日期} 的记录取代，见下方`；不物理删除任何旧条目。
- **待验证洞察被证实或证伪时：** 按 `已验证的核心洞察` 的格式写入新条目，并在原待验证条目末尾加 `⚠️ 已于 {slug} 验证 / 证伪`。

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
📁 文件：campaigns/{slug}/report.md

📌 执行摘要

   · 最大成功因素：{一句话}
   · 最大改进项：{一句话，归因到具体动作}
```
